# Performance tuning

Tune the TopGun server for your workload: memory ceiling, eviction thresholds, write-behind buffer, and connection limits. Env-var-configurable knobs are documented below. Deeper configuration (concurrency, timeouts, connection buffers) requires programmatic `ServerConfig` / `ConnectionConfig` struct fields.

## Memory and eviction

The server uses an in-memory record cache with LRU eviction. When memory usage rises above the high-water mark, the eviction orchestrator removes least-recently-used records until it drops to the low-water mark.

All four env vars below are real — sourced from `packages/server-rust/src/storage/eviction_config.rs`:

<div className="not-prose">
  <CodeBlock title=".env" language="bash" code={memoryEnvCode} />
</div>

| Variable | Default | Source | Notes |
|----------|---------|--------|-------|
| `TOPGUN_MAX_RAM_MB` | `1024` | `eviction_config.rs:85` | RAM ceiling in MB; eviction engages above high-water mark |
| `TOPGUN_EVICTION_HIGH_PCT` | `85` | `eviction_config.rs:105` | Percent of ceiling at which eviction starts (0–100) |
| `TOPGUN_EVICTION_LOW_PCT` | `70` | `eviction_config.rs:125` | Percent of ceiling at which eviction stops; must be &lt; high |
| `TOPGUN_EVICTION_INTERVAL_MS` | `1000` | `eviction_config.rs:145` | Orchestrator tick interval in ms |

**Why 1024 MB / 85 / 70 defaults?** Conservative ceiling tuned for a single-node HN-demo server. 85/70 water marks follow the Hazelcast LRU eviction reference pattern — wide enough gap (15 pp) to avoid eviction churn under bursty write loads. See [Configuration defaults rationale](/docs/deploy/configuration#defaults-rationale).

## Write-behind buffer

The write-behind layer decouples mutation latency from persistence latency by buffering writes in per-partition coalesced queues and flushing on a configurable schedule.

All three env vars below are real — sourced from `packages/server-rust/src/storage/datastores/write_behind.rs`:

<div className="not-prose">
  <CodeBlock title=".env" language="bash" code={writeBehindEnvCode} />
</div>

| Variable | Default | Source | Notes |
|----------|---------|--------|-------|
| `TOPGUN_WRITEBEHIND_FLUSH_INTERVAL_MS` | `100` | `WriteBehindConfig::flush_interval_ms` | The longest a buffered write waits while the flush task is idle; there is no write delay; a pass cut by its limit (1000 writes or 8 MiB) is followed by the next at once, and after a pass that took every due write the flush task waits up to this interval. New-key admission is bounded by about `capacity / (interval + 2 × pass time)`, so a value of 500 or more (with a non-zero capacity) logs a startup warning; `0` refuses to start |
| `TOPGUN_WRITEBEHIND_BATCH_SIZE` | `100` | `WriteBehindConfig::batch_size` | Accepted and without effect: a flush pass takes at most 1000 entries or 8 MiB of encoded values, whichever comes first — fixed limits — and stores them in one engine commit, so the value neither groups nor limits the pass. On RocksDB that commit is not synced: the WAL holds every frame of the pass, and the store is made durable by the store sync of each WAL collection tick (every 5 s) and of a clean stop, both before any WAL frame they cover is collected. It is not honoured on purpose: the documented example value `100` would cut every pass tenfold on deployments that copied it. |
| `TOPGUN_WRITEBEHIND_CAPACITY` | `10000` | `WriteBehindConfig::capacity` | Soft bound on buffered keys, so the write buffer cannot grow without limit: a write of a key that is not already buffered is refused once this many keys are buffered (`0` means unlimited). It is not a hard limit — the count can exceed it by the writes of new keys that passed the check at the same moment (`W`), plus one re-write of each key the running flush pass holds (`H`): `buffered <= C - 1 + W + H`, with `H <= min(L, C - 1 + W)`, because a pass holds at most `L` = 1000 of the entries that were due when it began. In the worst case the count reaches up to about twice the capacity. A key stays counted until its entry is persisted or retired into a newer write of the same key; an entry the store refuses is neither, and stays counted until the store takes it. So while the store refuses writes the buffer stays at its bound, and every write of a key that is not already buffered is refused until the store returns. A refused write is not acknowledged: the server answers with the transient `internal` error (code 500), and the client keeps the operation and sends it again; each such refusal counts in `topgun_write_behind_capacity_refusals_total{bound="keys"}`. The memory of the buffered values has its own bound, `TOPGUN_WRITEBEHIND_CAPACITY_MB`. `TOPGUN_WRITEBEHIND_CAPACITY=0` together with a store that refuses writes is not supported: nothing then limits the number of buffered keys. |
| `TOPGUN_WRITEBEHIND_CAPACITY_MB` | `256` | `WriteBehindConfig::capacity_bytes` | Soft bound on the memory of the buffered values, in MiB (`0` disables it). Values are counted at a structural estimate of their stored encoding (not heap bytes), held once; an OR slot at its cost. At or above the budget a plain write that grows its key's buffered value is refused, and so is every in-place OR write — OR add and remove, tombstone prune, the TTL sweep's OR removals, a client's OR push diff — before it changes anything. A remove, a `remove_all`, an LWW write of a top-level `null` and a rewrite that does not grow are never refused by the byte bound; the key bound still refuses a remove of a key that is not buffered at the key capacity. A single value larger than the budget is admitted into a buffer below it. A refusal is the transient `internal` error (500, `Write-behind byte capacity exceeded`), the client resends, and it counts in `topgun_write_behind_capacity_refusals_total{bound="bytes"}`; a pushed OR diff is merged up to the refused entry and the rest at the client's next connection. Not a hard limit: it can be exceeded by the writes already past the check and by rewrites of keys a flush pass holds. An unparseable value warns and uses the default; a value whose bytes do not fit in 64 bits ends the process with the panic message on stderr and exit status 101. It adds to `TOPGUN_MAX_RAM_MB`. |
| `TOPGUN_WAL_FSYNC_POLICY` | `batched` | `write_behind.rs` | WAL fsync aggressiveness: `batched` (default, throughput) \| `per_op` (acked == durable under `kill -9`) \| `none` (tests only) |

**Durability note:** The default `TOPGUN_WAL_FSYNC_POLICY=batched` acks a write once its WAL frame is appended, then fsyncs on a ~10 ms group-commit timer — so an unclean `kill -9` can drop the last few milliseconds of acked writes. This is a deliberate throughput default for demo-tier single-node deployments; the originating client keeps the write in local storage and re-converges on reconnect. **If you need acked-implies-durable, set `TOPGUN_WAL_FSYNC_POLICY=per_op`** (every WAL frame is fsynced before the write acks) — expect materially lower write throughput in exchange. Separately, the write-behind buffer holds an acked write until its next flush pass — with no write delay, at most the 100 ms idle interval plus a pass when the server is idle — before persisting it to the durable backend; crash-safe shutdown drain + WAL recovery are tracked separately (out of scope for this release).

## Programmatic tuning

Deeper configuration is controlled via Rust struct fields, not env vars. To change these values, modify the config structs and rebuild the binary.

<AlertBox variant="info" title="Not env-var configurable today" text="These fields are Rust struct defaults. Env-var overrides for concurrency, timeout, and connection-buffer settings are tracked at TODO-400. Until then, modify the config structs and rebuild." />

### ServerConfig fields

| Field | Default | When to adjust |
|-------|---------|----------------|
| `max_concurrent_operations` | 1000 | Increase when load-shed errors appear under high load |
| `default_operation_timeout_ms` | 30000 ms | Decrease for faster failure detection; increase for complex queries |
| `max_query_records` | 10000 | Increase for large dataset queries; decrease if memory constrained |
| `gc_interval_ms` | 60000 ms | Decrease if stale data accumulating; increase if GC overhead visible |

### ConnectionConfig fields

| Field | Default | When to adjust |
|-------|---------|----------------|
| `outbound_channel_capacity` | 256 | Frames queued per connection. A subscriber whose queue is full when a live event is due (a map, query or search update) is disconnected, and resyncs its maps, queries and searches when it reconnects. Raising the capacity absorbs longer bursts; it is not needed for correctness. A client that both writes heavily and subscribes can be disconnected when its own acknowledgements fill its queue at the moment another writer's event is due. Decrease if per-connection memory is high |
| `slow_consumer_drop_threshold` | 256 | Drops in a row of a best-effort push (Event Journal, counter, partition map) after which a client is disconnected; `0` disables it. It does not govern live map, query or search events: their first miss disconnects whatever this value is, `0` included |
| `idle_timeout` | 60s | Decrease to reclaim idle connections; increase if frequent reconnects |
| `ws_write_buffer_size` | 128 KB | The per-connection write buffer: once it holds more than this, it is written out to the socket. Messages of any size are delivered; this does not limit them. Raising it shortens the outbound fragment (`ws_max_write_buffer_size − ws_write_buffer_size − 10` bytes), and it must stay below `ws_max_write_buffer_size` |
| `ws_max_write_buffer_size` | 512 KB | The most a connection's write buffer may hold, and so its memory. An outbound message larger than `ws_max_write_buffer_size − ws_write_buffer_size − 10` bytes (393 206 at the defaults) is sent as WebSocket continuation frames of at most that size; raising this only makes the frames larger |
| `outbound_chunk_len` | 64 KiB | On a connection opened with `tg_chunks=1` (the TypeScript client's single-server connection), a message longer than this is sent as `CHUNK` messages of at most this many bytes, so a client on a slow link sees one complete every 64 KiB and its heartbeat does not reconnect while a large response arrives. Capped at `ws_max_write_buffer_size − ws_write_buffer_size − 42`; below a 33-byte frame budget no connection is chunked. Not read from the environment |

### NetworkConfig fields

| Field | Default | When to adjust |
|-------|---------|----------------|
| `request_timeout` | 30s | Decrease to fail hung requests faster |
| `max_body_size` | 2 MB | Increase for large batch writes |
| `rate_limit_per_ip` | 100 req/s | Decrease to throttle aggressive clients |
| `rate_limit_burst` | 50 | Decrease to tighten burst tolerance |
