# Authentication & Security

Authentication and security: connect any JWT-issuing provider (Clerk, BetterAuth, Firebase, or custom) to your `TopGunClient` instance; the client sends the token to the server on every WebSocket handshake; the server validates it and enforces per-collection RBAC access control. Local-first writes happen before the network authenticates, so offline clients can write immediately and reconcile permissions on reconnect.

## Setup

Create the client once and export it. The `storage` field accepts `new IDBAdapter()` (zero-arg) for IndexedDB persistence in the browser.

export const setupCode = `import { TopGunClient } from '@topgunbuild/client';
import { IDBAdapter } from '@topgunbuild/adapters';

export const tgClient = new TopGunClient({
  serverUrl: 'ws://localhost:8080',
  storage: new IDBAdapter(),
});`;

  <CodeBlock title="src/lib/topgun.ts" language="typescript" code={setupCode} />

Register a token provider after the client is created. The client calls it once for every connection it opens, and again before the current token expires, to refresh the open connection in place (see [Token lifecycle and refresh](#token-lifecycle-and-refresh)).

export const tokenProviderCode = `// The provider must return a valid JWT or null.
// Returning null leaves the connection unauthenticated.
tgClient.setAuthTokenProvider(async () => {
  const token = await yourAuthProvider.getToken();
  return token ?? null;
});

await tgClient.start();`;

export const clerkSyncCode = `import { useEffect } from 'react';
import { useAuth } from '@clerk/clerk-react';
import { tgClient } from '../lib/topgun';

// Mount this once near the root of your app, inside <ClerkProvider>
export function TopGunAuthSync() {
  const { getToken, isSignedIn } = useAuth();

  useEffect(() => {
    if (isSignedIn) {
      tgClient.setAuthTokenProvider(async () => {
        try {
          return await getToken();
        } catch {
          return null;
        }
      });
    }
  }, [isSignedIn, getToken]);

  return null;
}`;

### Clerk JWT_SECRET (production)

Clerk uses RSA asymmetric signing. Set `JWT_SECRET` to the RSA public key from Clerk's JWKS endpoint:

```
https://YOUR_CLERK_DOMAIN.clerk.accounts.dev/.well-known/jwks.json
```

export const clerkProductionCode = `# Docker / Dokploy — use escaped newlines:
JWT_SECRET="-----BEGIN PUBLIC KEY-----\\nMIIBIjAN...AQAB\\n-----END PUBLIC KEY-----"

# Shell script — use real newlines:
export JWT_SECRET="-----BEGIN PUBLIC KEY-----

### Bridge endpoint: BetterAuth session → TopGun JWT

export const betterAuthBridgeServerCode = `import { auth } from '../lib/auth';
import jwt from 'jsonwebtoken';

const JWT_SECRET = process.env.JWT_SECRET!;

// POST /api/topgun-token
// Verifies the BetterAuth session cookie and mints a TopGun JWT.
export async function GET(request: Request) {
  const session = await auth.api.getSession({ headers: request.headers });

  if (!session?.user) {
    return new Response('Unauthorized', { status: 401 });
  }

  const token = jwt.sign(
    { sub: session.user.id, roles: session.user.roles ?? ['USER'] },
    JWT_SECRET,
    { expiresIn: '1h' },
  );

  return Response.json({ token });
}`;

<div className="not-prose">
  <CodeBlock title="server/api/topgun-token.ts" language="typescript" code={betterAuthBridgeServerCode} />
</div>

export const betterAuthBridgeClientCode = `import { tgClient } from './topgun';

let cachedToken: string | null = null;

tgClient.setAuthTokenProvider(async () => {
  if (cachedToken) return cachedToken;
  const res = await fetch('/api/topgun-token', { credentials: 'include' });
  if (!res.ok) return null;
  const { token } = await res.json();
  cachedToken = token;
  return token;
});

export function clearTopGunToken() {
  cachedToken = null; // Call on logout to force re-auth on next reconnect
}`;

## Custom auth provider

If you manage your own JWT issuance (e.g. a custom login endpoint), call `setAuthTokenProvider` with an async function that returns the token from your session store.

export const customJwtCode = `import jwt from 'jsonwebtoken';

// Server side: generate a JWT for a verified user
export function generateToken(user: { id: string; roles: string[] }) {
  return jwt.sign(
    { sub: user.id, roles: user.roles },  // sub is the only required claim
    process.env.JWT_SECRET!,
    { expiresIn: '24h' },
  );
}`;

export const customClientCode = `import { tgClient } from './topgun';

let cachedToken: string | null = null;

tgClient.setAuthTokenProvider(async () => {
  if (cachedToken) return cachedToken;
  try {
    const res = await fetch('/api/token', { method: 'POST', credentials: 'include' });
    if (!res.ok) return null;
    const { token } = await res.json();
    cachedToken = token;
    return token;
  } catch {
    return null;
  }
});

export async function login(email: string, password: string) {
  const res = await fetch('/api/login', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ email, password }),
  });
  const { token } = await res.json();
  cachedToken = token;
}

export function logout() {
  cachedToken = null;
}`;

## Firebase integration

Firebase uses RS256 for JWT signing. Obtain the Firebase public key from the Google JWKS endpoint and set it as `JWT_SECRET`.

| Provider | Algorithm | JWT_SECRET value |
|----------|-----------|-----------------|
| Custom / self-hosted | HS256 | Shared secret string |
| Clerk | RS256 | RSA public key (PEM) |
| Firebase | RS256 | RSA public key (PEM) |
| Auth0 | RS256 | RSA public key (PEM) |

The TopGun server detects RSA keys automatically (by checking for `-----BEGIN`) and switches to RS256 validation.

## JWT token structure

TopGun takes the caller from the `sub` and `roles` claims (and checks `exp`, and `iss` / `aud` when they are configured). It also reads the tenant claim when `TOPGUN_TENANT_CLAIM` is set, the guest claim when `TOPGUN_GUEST_CLAIM` is set (see [Guest tokens](#guest-tokens)), and checks the type of the reserved `tg_link` claim:

export const jwtPayloadCode = `{
  "sub": "user_123",    // User ID — required per RFC 7519
  "roles": ["USER"],    // Array of roles for RBAC (optional)
  "iat": 1699000000,    // Issued at
  "exp": 1699086400     // Expiration
}`;

## Guest tokens

An anonymous visitor (a shopper on a store page, a reader of a public board) can get an identity of its own: a **guest token**. TopGun does not mint guest tokens; your app backend does, with the same secret or key it signs user tokens with.

Turn guest principals on by naming the claim that marks a guest token:

```bash
TOPGUN_GUEST_CLAIM=tg_guest
```

With the variable set, a token whose `tg_guest` claim is `true` is a guest; a token without the claim, or with `false`, is a user. Any other value (`"true"`, `1`, `null`, an object) refuses the token, on the WebSocket handshake and on HTTP `/sync`, before a custom validator runs. With the variable unset, every token is a user and the claim is never read. The server refuses to start (exit 1) when the variable is set but empty, is not valid Unicode, is set together with `TOPGUN_NO_AUTH`, names `sub`, `roles`, `exp`, `iat`, `nbf`, `iss`, `aud` or `tg_link`, or names the same claim as `TOPGUN_TENANT_CLAIM`. The startup summary line reports `guest_claim` (`off` or the claim name).

A guest token from your backend looks like this; with `TOPGUN_TENANT_CLAIM` set, the backend puts the tenant claim in it too, since a guest token without it is refused like any other token:

```json
{
  "sub": "guest_4f9c2e7a1b8d4c6e9a0f3b5d7e1c2a48",
  "tg_guest": true,
  "exp": 1699000900
}
```

How to mint them safely:

- **Generate the `sub` on the server.** Make it at least 128 random bits, once per visitor, and keep it server-side or in a cookie your backend signs, so that minting again for the same visitor returns the same `sub`. Deriving `sub` from a value the client controls (a raw cookie value, a device id the client chose) is unsafe: anyone can claim another visitor's identity by sending that value.
- **Keep guest subs apart from user ids**, for example with a prefix no user id carries, or write policies that branch on `auth.kind`.
- **Give guest tokens a short `exp`.**
- **Guest tokens never reach the admin HTTP API.** It refuses a guest token with 403, whatever its roles, and a token whose guest claim is not a boolean with 401.
- **Create your policies before you admit guests.** With no policy ever configured, every operation is allowed, guests included.

In policies, a guest is `auth.kind == 'guest'` and a user `auth.kind == 'user'` (see [RBAC conditions](/docs/guides/rbac#conditions)). A guest never gets the policy admin bypass: a guest whose `sub` is listed in `TOPGUN_ADMIN_SUBJECTS` is evaluated against the policies like anyone else.

`tg_link` is reserved for linking a guest to the user it becomes; it is not honoured yet. A token whose `tg_link` is a string is admitted and the claim is ignored; one whose `tg_link` has any other type is refused. This check runs whether or not `TOPGUN_GUEST_CLAIM` is set.

Server versions before guest principals ignore `TOPGUN_GUEST_CLAIM`: if you roll back, guest tokens are users there, and a guest whose `sub` is on `TOPGUN_ADMIN_SUBJECTS` would get the bypass. Keeping guest subs apart from user ids avoids that.

## Token lifecycle and refresh

- **A WebSocket connection closes when its token expires.** At the token's `exp` plus the server's clock-skew leeway (60 seconds) the server sends `AUTH_FAIL` with `code: 4401` and closes the connection. A token already past that point is refused at the handshake with the same code. `4401` and `4409` are values of `AUTH_FAIL.code`; the WebSocket close frame carries the normal close code. The counter `topgun_ws_token_expiry_closes_total` counts these closes.
- **Turning it off.** `TOPGUN_CLOSE_ON_TOKEN_EXPIRY=false` (or `0`, `off`, `no`, in any case) keeps connections open past `exp`, as earlier versions did; `true`, `1`, `on`, `yes` or leaving it unset keeps the closing on. Any other value, the empty string included, stops the server at startup. The startup summary line reports `close_on_token_expiry`.
- **Refreshing on an open connection.** A client can send a new `AUTH` message on an authenticated connection. If the token verifies and names the same principal (the same `sub`, tenant, kind and set of roles, in any order), the server answers `AUTH_ACK` without a `deviceToken` (a `deviceToken` in the message is ignored) and the connection now closes at the new token's `exp` plus the leeway, even when that is earlier. Anything else ends the connection: `AUTH_FAIL` with `code: 4409` for a token that names another principal, `code: 4401` for an expired one, no code for any other refusal, each followed by the close. A connection never changes who it is: to switch from a guest to a user, or to change roles, open a new connection. A refresh is checked whether or not the closing is turned off. A server started with `TOPGUN_NO_AUTH` ignores the message.
- **What the deadline does not cover.** Until the leeway runs out the connection still receives live updates and its operations are served, and operations accepted before the deadline finish after it. The deadline is computed once, from the server's clock, when the token is accepted; a later change of the server clock does not move it. A refresh counts against the connection's rate limit like an operation; one refused with the rate-limit error has to be sent again before the deadline. The server checks a refresh, custom validator included, before it reads the connection's next message. HTTP `/sync` checks `exp` on every request instead; a request whose token is expired or otherwise refused is served as an anonymous caller.
- **Clients that hold one token.** The MCP server (`@topgunbuild/mcp-server`) sets one token from its configuration, and `ClusterClient` has no token provider and does not refresh on an open connection. With the closing on, give each a token whose `exp` outlives its session, or start the server with `TOPGUN_CLOSE_ON_TOKEN_EXPIRY=false`.
- **The client refreshes for you.** With `setAuthTokenProvider`, the client asks the provider again before the current token's `exp`: at `max(30 s, R − min(60 s, R / 2))` after the server acknowledged the token, `R` being the time left until `exp` (for a 15-minute token, a minute before it expires). If the provider returns a different token, the client sends it on the open connection; its state, queries and subscriptions are kept. If it returns the same token, `null`, or throws, the client sends nothing and asks again later, never sooner than 30 seconds. A refresh that gets no answer within 10 seconds leaves the connection open and is not repeated on it; the connection then closes with `4401` at its deadline and the client reconnects. The same happens when the acknowledgement of a refresh is lost. A static token set with `setAuthToken` is never refreshed.
- **After an expiry close.** When the server refuses a token as expired (`4401`), the client never sends that token, or one whose `exp` is not later, again. With a provider, it closes the connection and asks the provider again, after 1 second doubling up to 30 seconds, without opening a connection, until the provider returns a newer token, and then reconnects with it. Without a provider, it drops the token and calls `onAuthRequired`. Any other refusal is retried through the ordinary reconnect, so a short outage of your token validator does not need a new token. Client versions before this behaviour reconnect after the close and send whatever their provider returns, or wait for a new token if they have none.
- **Switching from a guest to a user.** When a guest logs in, call `setAuthTokenProvider(userProvider)`. On a connected client it closes the connection and opens a new one as the user, which goes on refreshing through `userProvider`. `setAuthToken(userToken)` reconnects the same way, with a static token. Writes still pending are sent again under the user, and the server checks them against the user's policies: a write the user may not make is reported on `onWriteRejected` (see [Per-operation verdicts](/docs/reference/protocol#per-operation-verdicts)), and it is not retried or moved to the user. To keep guest writes, let them reach the server before switching (`getPendingOpsCount()` is `0`). A refresh whose provider returns a token for another principal ends the connection with `4409`; the client keeps that token and reconnects with it.
- **Tabs and devices.** Every client instance, each browser tab included, has its own connection, refreshes on its own schedule and calls the provider on its own, so the endpoint that mints guest tokens should return the same `sub` for the same visitor on every call.
- **On reconnect.** When the connection drops (page reload, network drop), the client opens a new one and calls the provider for its token.
- **Returning `null` from the provider leaves the connection unauthenticated.** No data operations are permitted in that state.
- **Recommendation:** your token provider should call your app's token or session refresh endpoint rather than relying on a cached token that may be stale after a long offline period.
