# RBAC — role-based access control

TopGun enforces **per-collection, per-operation** access control on the server. A Tower middleware layer checks every client read, write, and remove against a policy store before the operation reaches the domain services. This is shipped and active today — you do **not** need to re-implement authorization in your application code. App-layer claim checks are fine as optional defense-in-depth, but server-side enforcement is the authoritative gate.

## Two server-side gates: admission, then authorization

Every client operation passes through two distinct server-side gates, in order. They answer different questions, and only the second one is authorization:

1. **Admission** — a cheap, identity-agnostic integrity and quota gate at the edge. It does not decide *who may touch which collection*; it only rejects malformed or unauthenticated traffic before any policy is consulted. Its responsibilities are: enforce the authentication baseline (`require_auth`), deny anonymous writes, cap payloads at the value-size limit (`max_value_bytes`), sanitize incoming HLC timestamps, and route by trusted origin.
2. **Authorization** — **RBAC is the sole authorization layer**, and it is the policy engine described in the rest of this page. Once a request clears admission, RBAC is the only thing that decides whether a given principal may `read`, `write`, or `remove` a given collection.

| Gate | Question it answers | Identity-aware? | Mechanism |
|------|---------------------|-----------------|-----------|
| Admission | Is this request well-formed, authenticated, and within limits? | No | `require_auth`, deny-anonymous-writes, `max_value_bytes`, HLC sanitization, trusted-origin routing |
| Authorization | May *this principal* perform *this action* on *this collection*? | Yes | RBAC policies (this page) |

There is exactly one authorization layer — RBAC. Admission is a guard, not a second set of permissions, so there is no per-map ACL or any other authorization mechanism to configure alongside it.

## How evaluation works

Authorization runs on every client operation (`read`, `write`, `remove`):

1. **Admin bypass** — a principal whose roles include `admin` is always allowed.
2. **Permissive default** — if the policy store is empty, all operations are allowed, so an unconfigured deployment behaves exactly as before. RBAC "activates" the moment you create your first policy.
3. **Allow-list once active** — with at least one policy present, a map is evaluated against the policies whose pattern matches it. The principal needs a matching `allow` for the action.
4. **Deny-wins** — if any matching policy denies the action, the result is `Deny`, regardless of allow rules.
5. **Default-deny for uncovered maps** — once any policy exists, a non-admin operation against a map with no matching `allow` is denied.

### What counts as a read and a write

Every operation that names a map is checked against that map: queries, searches (full-text, hybrid and vector), sync, journal reads and subscriptions are reads; record writes, entry processors and conflict resolver registration and removal are writes. Pub/sub topics are matched by the same patterns: publishing to a topic is a write on its name, subscribing is a read. A journal read or subscription that names no map is allowed, and returns only the events of the maps the principal may read.

## Policy model

A policy is a single rule binding a map pattern + action to an allow/deny effect, with an optional condition:

| Field | Type | Meaning |
|-------|------|---------|
| `id` | string | Stable identifier. Generated as a UUID if omitted on create. |
| `mapPattern` | string (glob) | `*` matches all maps; `users.*` matches `users.profiles`, `users.settings`, etc. |
| `action` | `read` \| `write` \| `remove` \| `all` | The operation governed. `all` covers every action. |
| `effect` | `allow` \| `deny` | Whether a match grants or denies access. |
| `condition` | predicate (optional) | Rule only applies when the condition evaluates true against the record data and auth context. |

### Map patterns

Patterns split map names on `.`. A segment that is exactly `*` matches one segment, so `users.*` matches `users.profiles` but not `users` or `users.a.b`; a segment that is exactly `**` matches zero or more, so `users.**` covers the whole `users` namespace. A lone `*` matches every map. Any other segment is compared literally, including one that contains a `*`: `users/*` or `user*` matches only the map spelled that way, not the maps you probably meant. Name maps with `.` between their parts and put wildcards in whole segments.

### Tenants

When the server runs with `TOPGUN_TENANT_CLAIM`, every client token carries a tenant, and a client of tenant `acme` reaches only maps, topics, counters and locks whose names start with `acme.`. That boundary is checked before any policy and does not depend on one: no policy, admin subject or empty policy store lets a client reach another tenant's names. Policies then decide what a client may do inside its own tenant. To write one rule for every tenant, put the wildcard in the tenant segment: `*.orders` matches `acme.orders` and `globex.orders`. [Tenants and tenant deletion](#tenants-and-tenant-deletion) below has the whole model.

## Defining policies (admin API)

Policies are managed over the admin HTTP API. The endpoints require an **admin bearer token** (mint one by logging in with the operator credentials — see [self-hosting](/docs/deploy/self-host)).

```http
POST   /api/admin/policies        # create (or upsert with an explicit id)
GET    /api/admin/policies        # list all policies
DELETE /api/admin/policies/{id}   # delete by id (204 even if absent)
```

Create an allow rule that lets any authenticated user read the `articles` map:

```bash
curl -X POST https://api.example.com/api/admin/policies \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "mapPattern": "articles",
    "action": "read",
    "effect": "allow"
  }'
```

Add a deny rule — deny-wins, so this blocks writes to anything under `admin.*` even if a broader allow exists:

```bash
curl -X POST https://api.example.com/api/admin/policies \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "mapPattern": "admin.*",
    "action": "write",
    "effect": "deny"
  }'
```

## Tenants and tenant deletion

A tenant is a prefix of map names bound to a claim of the client's token. Turn tenancy on by setting `TOPGUN_TENANT_CLAIM` to the name of the top-level JWT claim that carries the tenant, taken verbatim (a namespaced claim such as `https://example.com/tenant` works). Unset, tenancy is off and the claim is never read.

**Choose a claim users cannot edit.** The server checks only the form of the tenant, never where it came from. `TOPGUN_TENANT_CLAIM`, and `tenantClaim` in a token-exchange provider's `claims` mapping, must name a claim your identity provider sets and users cannot change — an organization id, not a profile field. A claim a user can edit lets that user pick any tenant.

**Claim rules.** With tenancy on, every client token on the WebSocket handshake and on HTTP `/sync` must carry a tenant of 1 to 128 characters from `A-Z`, `a-z`, `0-9`, `_` and `-` that does not start with `_topgun_` or `__topgun_` in any letter case. A token without one is refused like a token without `sub`. There is no exemption by subject, role or origin.

**Naming.** A tenant `acme` owns every name `acme.<anything>`: maps such as `acme.orders` and `acme.users.profiles`, and topics, counters and locks named the same way. `acme` does not own `acmecorp.orders` (the `.` is part of the prefix).

**What is refused.** A client of tenant `acme` is refused every operation on a name it does not own: writes and reads, queries and subscriptions, search, hybrid and vector search, sync, journal reads of another tenant's map, topics, counters and locks. A journal read or subscription without a map returns only the tenant's events. `SqlQuery` is refused with tenancy on.

**The admin plane is the only cross-tenant client.** The admin API (`/api/admin/*`) works across tenants and refuses any token that carries the tenant claim (403), so an admin token is minted without one.

**Token refresh.** A token minted by `/api/auth/refresh` carries no tenant and would be refused with tenancy on. The server binary does not wire refresh tokens, and it does not serve token exchange (`/api/auth/token`) either.

**Isolation is logical.** All tenants share one store and one WAL; a tenant is a name prefix, not a separate store. A store per tenant is deferred until a hosted product needs it.

### Deleting a tenant

```http
DELETE /api/admin/tenants/{tenant}   # admin bearer token
```

Deleting tenant `acme` removes every map it owns from the store, including maps whose first write is still buffered, and the scalar and vector index descriptors of those maps. Before anything is written the server refuses — and changes nothing — when tenancy is off (409), when RBAC is not configured (409: the delete writes a deny policy, which would turn a deployment without policies default-deny for everyone), and for an invalid tenant (400). Otherwise it:

1. writes the policy `tenant-deleted:acme` — `mapPattern` `acme.**`, `action` `all`, `effect` `deny` — so the tenant's clients are refused from then on and cannot push their copies back;
2. drops the maps once every write of them is durable;
3. removes the index descriptors of every owned map the drop removed.

It answers `200` with `{ "dropped": [...], "failed": [], "message": "..." }`. Running it again is safe and finishes what an earlier run left. Every answer other than one of the refusals above leaves the tenant denied:

- `409` — another tenant delete is running on the node, or the store cannot delete a tenant (`STORAGE_BACKEND=null`); this request deleted nothing. Run it again.
- `503` with `failed: [{ "map", "error" }]` — the maps listed are still stored; the descriptors of those maps are kept. Run it again.
- `503` with no `failed` maps — the store refused the drop (for example, a write it keeps refusing holds the drop past `TOPGUN_WRITEBEHIND_SHUTDOWN_TIMEOUT_MS`), or the index descriptor file could not be written. Data may be partly deleted. Run it again.
- `503` naming the deny policy — the policy could not be written; nothing was closed or deleted.

An accepted delete runs to the end even if the client disconnects; its outcome is logged as `tenant delete finished` (`tenant`, `dropped`, `failed`, `error`), at `INFO` on success and `WARN` otherwise.

What a delete does not do:

- **Deletion is logical.** The values stay in sealed WAL segments until they are collected, in backups, in the in-memory event journal until evicted, and in a kept `.pre-migration` store file — a rollback to that file brings deleted tenants back.
- **In-memory copies stay until restart.** Until the server restarts, the admin data plane may still show the deleted maps, and background work (rehydration, tombstone pruning, expiry) that touches a resident copy is refused and logs it. Subscriptions made before the delete stay registered but receive nothing, since every write is refused.
- **Admin subjects bypass the deny policy.** A subject on `TOPGUN_ADMIN_SUBJECTS` is not refused by the policy; until the server restarts its writes to the tenant's maps are refused by the delete itself. Remove the tenant's subjects from that list before you re-enable the tenant or restart.
- **Locks stay usable.** A deleted tenant's clients can still take and release locks on its own names, also after a restart: locks skip the policy check and hold no data. Its topics and counters are refused by the deny policy.
- **A typo is still a delete.** Deleting a tenant name that never existed writes its deny policy and closes the name until the server restarts.
- **One stuck write blocks every delete.** A WAL frame left unreplayed at boot (the `BootUnreplayed` alarm), or a write the store keeps refusing in any map, makes every tenant delete on the node answer `503` until it is resolved or the server restarts and replays it. A delete can also start the stalled-watermark `ERROR` line for WAL partitions that were idle.

**Re-onboarding a deleted tenant:** delete the `tenant-deleted:acme` policy (`DELETE /api/admin/policies/tenant-deleted:acme`) **and restart the server** — the store keeps refusing the tenant's writes for the rest of the process.

## Conditions

A policy can carry a condition that is evaluated against the record `data` and the caller's auth context. Conditions reference `data.<field>` and `auth.id` / `auth.roles`. The simplest way to express one is the `conditionExpr` string, a CEL-like expression parsed server-side:

```bash
# Owners can write only their own records
curl -X POST https://api.example.com/api/admin/policies \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "mapPattern": "documents",
    "action": "write",
    "effect": "allow",
    "conditionExpr": "auth.id == data.ownerId"
  }'
```

More expression examples:

```text
auth.id == data.ownerId
data.role in auth.roles || data.public == true
data.x == 'hello' && (auth.role == 'admin' || auth.role == 'editor')
```

Supported operators: `==`, `!=`, `>`, `<`, `>=`, `<=`, `in`, `contains`, `containsAll`, `containsAny`, `startsWith`, `endsWith`, combined with `&&`, `||`, `!`, and parentheses. Values are strings (`'...'`), numbers, or booleans. If you prefer to pass a structured predicate directly, send a `condition` JSON object instead — it takes precedence over `conditionExpr`.

## Roles

Roles come from the authenticated principal (the JWT validated on the WebSocket handshake — see [Authentication](/docs/guides/authentication)). The `admin` role short-circuits evaluation and is always allowed. Other roles are matched inside conditions via `auth.roles` (e.g. `data.role in auth.roles`).

## Persistence

On the embedded store (the default, `STORAGE_BACKEND=redb`) policies are stored durably and survive a restart, including the marker that RBAC is configured: once any policy has been written, a store emptied of policies denies by default. With `STORAGE_BACKEND=null` policies are kept in memory only and a restart clears them.

See the [roadmap](/docs/roadmap) for the status of durable policy storage and cluster-wide policy replication.
