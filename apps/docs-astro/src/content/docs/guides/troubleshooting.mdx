# Troubleshooting

This guide covers common issues you may encounter when using TopGun, organized by category.

---

## CRDT Merge Edge Cases

### Data reverted after reconnect

**Symptom:** After going offline and reconnecting, some of your local changes appear to revert to an older state.

**Cause:** TopGun uses Hybrid Logical Clocks (HLC) to order writes. Each write carries a timestamp of `{millis, counter, nodeId}`. When two clients write to the same field, the write with the higher HLC timestamp wins (Last-Write-Wins semantics). If your local clock is behind the server or another client, your writes may have lower timestamps.

**Solutions:**
- Ensure system clocks are reasonably synchronized (NTP). TopGun tolerates moderate clock skew, but large drift (minutes+) can cause unexpected ordering
- Check that `nodeId` is unique per client instance -- duplicate node IDs cause HLC collisions. A custom `nodeId` must also not contain `:`, `|` or `#` -- the client throws at construction if it does
- Remember that LWW is per-field, not per-record. Only the conflicting fields revert; other fields retain their values

### Concurrent edits lost

**Symptom:** Two users edit different items in a collection simultaneously, but one user's additions disappear after sync.

**Cause:** If you are using `LWWMap` for a collection where items are added and removed concurrently, LWW semantics may cause one write to overwrite another when they modify the same key.

**Solutions:**
- Use `ORMap` (Observed-Remove Map) for collections where concurrent additions and removals are expected. ORMap uses unique tags to track each add operation, allowing concurrent adds to coexist
- Reserve `LWWMap` for single-document fields where last-write-wins is the desired behavior
- See the [Data Structures guide](/docs/concepts/data-structures) for details on when to use each CRDT type

### Stale data after merge

**Symptom:** After a sync cycle completes, some records still show old values even though newer writes exist on the server.

**Cause:** MerkleTree-based delta sync compares hash digests to determine which records need syncing. If the sync was interrupted or only partially completed, some records may not have been transferred yet.

**Solutions:**
- Wait for the sync cycle to fully complete. Check the `SyncEngine` connection state -- it should transition to `connected` and then `synced`
- For large datasets, sync happens in batches. Initial sync after a long offline period may take several seconds
- If the issue persists, the client's local MerkleTree may be corrupted. Clearing IndexedDB storage and re-syncing will rebuild it from the server. Note: call `LWWMap.prune()` to remove tombstones if the map has accumulated many deleted entries before clearing

## WebSocket Connection Issues

### Connection drops repeatedly

**Symptom:** The client connects briefly then disconnects in a loop, or never establishes a stable connection.

**Solutions:**
- Verify the server address format: use `ws://` for local development and `wss://` for production (TLS)
- Check that the server is actually running and listening on the expected port
- If behind a reverse proxy (nginx, Cloudflare), ensure WebSocket upgrade headers are forwarded. Common nginx configuration:
  ```
  proxy_http_version 1.1;
  proxy_set_header Upgrade $http_upgrade;
  proxy_set_header Connection "upgrade";
  ```
- Increase proxy timeout settings. Many proxies close idle WebSocket connections after 60 seconds. TopGun sends heartbeats, but aggressive proxy timeouts can still cause drops

### Sync not working behind corporate proxy

**Symptom:** The application works on home WiFi but fails to sync in a corporate environment.

**Cause:** Many corporate proxies block WebSocket upgrade requests (`HTTP 101 Switching Protocols`) or filter non-HTTP traffic.

**Solutions:**
- Use `wss://` (WebSocket over TLS) which is harder for proxies to inspect and block
- If the proxy terminates TLS, you may need to configure the proxy to allow WebSocket upgrades
- Check with your network administrator whether WebSocket traffic is explicitly blocked
- TopGun clients automatically queue writes when offline and sync when connectivity is restored, so the application remains usable even if sync is intermittently blocked

### Authentication failed

**Symptom:** Connection is rejected with an authentication error, or the server returns a 401/403 status.

**Cause:** TopGun uses JWT tokens for authentication. The token must contain a `sub` (subject) claim per RFC 7519. The server validates the `sub` claim is present and non-empty; no custom `userId` field is required or supported.

**Solutions:**
- Verify your JWT token has not expired. Check the `exp` claim
- Ensure the token contains a `sub` claim with the user ID. TopGun uses only the standard `sub` claim — there is no custom `userId` field
- Verify the token is signed with the same secret or key pair configured on the server (`JWT_SECRET` env var)
- Check that the token is supplied via `setAuthToken` or `setAuthTokenProvider` after construction:
  ```typescript
  import { IDBAdapter } from '@topgunbuild/adapters';

  const client = new TopGunClient({
    serverUrl: 'wss://your-server.com',
    storage: new IDBAdapter(),
  });
  client.setAuthToken('your-jwt-token');
  // Or for refreshing tokens:
  // client.setAuthTokenProvider(async () => fetchFreshToken());
  ```

## IndexedDB Persistence

### Data gone after browser update

**Symptom:** After a browser update or clearing browser data, locally stored records are gone.

**Cause:** IndexedDB storage can be evicted by the browser under storage pressure, especially if the site is not installed as a PWA or if the user has not interacted with it recently.

**Solutions:**
- Request persistent storage to reduce eviction risk:
  ```typescript
  if (navigator.storage && navigator.storage.persist) {
    const granted = await navigator.storage.persist();
    console.log('Persistent storage granted:', granted);
  }
  ```
- Inform users that critical data is synced to the server. Local storage is a cache for offline access, not the sole source of truth
- Consider using a Service Worker to register the app as a PWA, which gives it higher storage priority

### Slow startup with large dataset

**Symptom:** The application takes several seconds to become interactive when there is a lot of data in IndexedDB.

**Cause:** On startup, the `IDBAdapter` loads stored records into memory to hydrate the local CRDT state.

**Solutions:**
- Use selective sync to limit which data is loaded at startup. Only subscribe to the maps and queries your initial view needs
- Paginate large collections using query limits rather than loading everything at once
- Consider using `fields` projection in queries to load only the fields you need for list views, then fetch full records on demand

## Server Startup

### Port already in use

**Symptom:** The server fails to start with "Address already in use" error.

**Solutions:**
- Check if another TopGun instance or other service is using the port:
  ```bash
  lsof -i :8080
  ```
- Kill the existing process or choose a different port:
  ```bash
  PORT=8081 cargo run --bin topgun-server --release
  ```
- If running in development, ensure previous server processes are terminated before restarting

### Server refuses to start: removed storage setting

**Symptom:** The server exits at startup with an error whose message begins with one of these sentences:

- `STORAGE_BACKEND=postgres is no longer supported: the Postgres backend has been removed.`
- `DATABASE_URL is set, but the Postgres backend has been removed and this server does not read it.`

**Cause:** The server keeps its data in an embedded store, because the Postgres backend has been removed. It refuses STORAGE_BACKEND=postgres, and it refuses to start while DATABASE_URL is set (an empty value counts as set), so a leftover variable cannot silently send your data to a different store than you expect.

**Solutions:**
- Unset `DATABASE_URL` (an empty value counts as set), and remove `STORAGE_BACKEND=postgres` if you set it. The server then starts on the embedded store (`STORAGE_BACKEND=redb`, the default). Check your shell, `.env` files, compose files and container environment.
- Data kept by the old Postgres backend is not read by this server. There is no migration tool: it remains available with the server built from the tag `postgres-backend-last`.
- See [Storage Backends](/docs/deploy/storage-backends) for the embedded store, its paths and backup
- If the server starts on the default embedded store and you see write failures, check that the data directory is writable (defaults to `./topgun-data`; override with `TOPGUN_DATA_DIR`)

### Server refuses to start with a store location or store migration line

**Symptom:** The server exits with code 1 at startup, before it listens, with an error that begins with `store location:` or `store migration:` (a refusal is also logged as one `ERROR` line).

**Cause:** The server keeps its store in a data directory (`TOPGUN_DATA_DIR`) and, once, migrates the store file of earlier versions (`TOPGUN_REDB_PATH`) into it. When the two paths do not say unambiguously which store to serve, it refuses rather than guess. A refusal creates, moves and deletes nothing: the old store file, the kept `.pre-migration` file and the marker file stay exactly as they were, and the data directory's records are unchanged. Fix the cause and start again. Below, `{D}` is the data directory, `{L}` the path `TOPGUN_REDB_PATH` names (default `./topgun.redb`), and `{K}` the kept file `{L}.pre-migration`. The `store location: data directory {D}` line logged just before the refusal shows the paths the server used (`data_dir`, `data_dir_source`, `legacy_path`).

**Solutions, by the line the server logged:**

- `store location: {VAR} is set but empty` — `TOPGUN_DATA_DIR` or `TOPGUN_REDB_PATH` is set to an empty value. Unset it to use the default, or set a path.
- `store location: TOPGUN_DATA_DIR ({D}) and TOPGUN_REDB_PATH ({L}) name the same place or one lies inside the other` — give the data directory and the old store path different places, neither inside the other, for example `/data/topgun-data` and `/data/topgun.redb`.
- `store location: {D} is not a store directory, an empty directory or absent` — the data directory holds files but no store (`engine.redb`), or is a file. Point `TOPGUN_DATA_DIR` at an empty or absent directory, or at the directory that holds your store.
- `store location: two stores found: {D} holds a store in the data-directory format and {L} is a table-per-map store file; the server serves only one. Move one of them aside: rename {L} to keep the data-directory store, or move {D} away to migrate {L} again` — an old store file was put back beside an existing data directory (for example restored from a backup, or after a rollback that left the data directory in place). Decide which one holds the data you want. To keep the data directory, rename the file at `{L}`; the server then writes its marker file there. To serve the old file, move `{D}` away; the next start migrates `{L}` into a new data directory.
- `store location: {L} is an empty file; an older binary would open it as an empty store. Delete it, and this server writes the marker file there` — delete the empty file; the next start writes the marker file in its place.
- `store location: {L} says the store was moved to a data directory, but {D} holds no store` — `{L}` holds the marker file, but `TOPGUN_DATA_DIR` points at a directory without a store. Point `TOPGUN_DATA_DIR` at the directory the marker file names (its second line says which), or restore that directory from your backup. The marker file is never a store, so the server does not migrate it.
- `store location: a pre-migration store file is kept at {K}, but {D} holds no store; restore the data directory, or rename {K} to {L} to migrate it again` — the data directory is missing after a migration. Restore it from your backup, or rename `{K}` to `{L}` so the next start migrates that file again (writes acknowledged after the first migration are not in it).
- `store migration: a pre-migration file already exists at {K}; move it away before migrating {L}` — a previous migration's kept file is in the way. Move `{K}` somewhere else (keep it until the new store is confirmed), then start again.
- `store migration: {L} is not a table-per-map store file` — the file at `{L}` is neither a store of an earlier version nor the marker file (an empty file counts). Point `TOPGUN_REDB_PATH` at your old store file, or move the file away to start with an empty store.
- `store migration: refusing to migrate {L}: … table(s) are not table-per-map store tables: …` — the old file holds tables that no TopGun version created (at most 20 are named). The file is left as it was. Check that `TOPGUN_REDB_PATH` names the TopGun store file and not another redb database.
- `store migration: refusing to migrate {L}: its path is not UTF-8` — move the file to a path whose name is valid UTF-8 and point `TOPGUN_REDB_PATH` there.
- `store migration: refusing to start: {available} bytes are free on the file system of {D}, {required} are needed (1.5 × the size of {L}, plus 64 MiB); nothing was changed` — free disk space on the data directory's file system (or point `TOPGUN_DATA_DIR` at a larger one) and start again. While the kept file exists the node needs about twice the disk of the store.
- `store migration: refusing to resume the migration from {source}: {reason}` — a migration was interrupted, and what is at the paths now no longer matches it. By reason:
  - `the store is being migrated from that file, not from {L}` — `TOPGUN_REDB_PATH` changed during the migration. Set it back to `{source}`; the next start resumes.
  - `{L} is not the table-per-map store file the copy reads` — the old file was moved or replaced during the migration. Put it back at `{L}`; the next start resumes.
  - `a pre-migration file already exists at {K}` — a kept file appeared during the migration. Move `{K}` away; the next start resumes.
  - `both {L} and {K} hold something; the copy is verified and only one of them may` — move aside whichever of the two is not the file the migration started from; the next start finishes the migration.
  - `neither {L} nor {K} holds the legacy file the verified copy was taken from` — put the old store file back at `{L}` or `{K}`, or move `{D}` away and start from your backup.
- `store migration: refusing to resume the migration from an unknown source: the mark cannot be read (…)` — the data directory holds an unfinished migration this server cannot read. Move `{D}` away and start again: the old file at `{L}` is migrated anew.
- `store migration: verification failed for {table}: {difference}; {D} is left unfinished and is refused until it is removed` — the copy in the data directory does not match the old file. The old file is untouched. Move `{D}` away and start again to migrate anew; if the failure repeats, keep the logs and the old file and report it.
- `store location: cannot write the stub at {L}` — the server could not write its marker file at `{L}`: check that the directory of `{L}` is writable by the server.

**Not a refusal:** `store location: TOPGUN_REDB_PATH names {L}, which is not read: TOPGUN_DATA_DIR ({D}) already holds a store` is a warning; the server starts on the data directory and leaves the file at `{L}` alone. Remove it, or point `TOPGUN_REDB_PATH` elsewhere, to silence it. `store format: the pre-migration store file is kept at {K}; delete it once this store is confirmed` is logged at every start while the kept file exists; delete `{K}` once you no longer need a way back (see [Storage backends](/docs/deploy/storage-backends)).

### Cluster nodes not discovering each other

<AlertBox variant="warning" title="Cluster mode is on the roadmap" text="Multi-node cluster discovery is on the roadmap. Single-node deployment is recommended pre-1.0. See /docs/roadmap for the cluster-safety status." />

**Symptom:** Multiple server nodes are running but not forming a cluster. Each node operates independently.

The following steps are forward-compatible troubleshooting guidance for when full cluster discovery ships:

- Verify that all nodes are configured with the same cluster name/identifier
- Ensure the cluster port (separate from the client-facing WebSocket port) is accessible between nodes. Check firewall rules
- Verify that nodes can resolve each other's hostnames or IP addresses
- Check that the seed node addresses are correctly configured in each node's cluster configuration
- Review server logs with `RUST_LOG=topgun_server=debug` to see cluster protocol messages and identify where discovery fails
