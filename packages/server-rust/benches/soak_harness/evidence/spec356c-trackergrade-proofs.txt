WHY THIS FILE EXISTS, IN ONE PARAGRAPH.
R0.5 point 3 opens "the grader is proven in BOTH directions before it is trusted (R6's own standard,
applied to itself)" and closes "a discrimination that is asserted rather than demonstrated is the
thing this clause exists to refuse" -- and then demonstrates RED on limbs (b) and (d) ONLY. Limbs
(a) and (c) were shown green-on-compliant and never RED on a genuinely broken input, which is
exactly what that closing sentence refuses. Limb (e) did not exist at all. This file closes both
gaps: five inputs, each built to break a specific limb, plus one built to break nothing so the
grader is shown capable of going GREEN at all -- without that last one every demonstrated direction
would be a RED and the discrimination would still be one-sided.

WHAT THIS FILE IS NOT. None of these five runs is the real grade. The real run -- the grader against
the actually-edited .specflow/todos/TODO-634.md -- belongs to wave 5 and is published in the
manifest's §10.x beside this file. Everything here is instrument proof.

NOTHING UNDER .specflow/ WAS MODIFIED TO PRODUCE THIS FILE. Every input is a COPY in a scratch
directory; the live tracker files were opened for reading only. That is also why the grader takes a
<todos-dir> argument at all: limb (a) can only be shown RED on a genuinely changed TODO-637.md, and
the only honest way to get one is to change a copy.

DEFECTS FOUND BY THESE RUNS, IN THE GRADER ITSELF
================================================================================================
These five inputs were run against a first draft of the grader and it FAILED three of them. All
three are recorded here rather than silently repaired, because a proof file that shows only the
final passing run proves the fixed grader and hides the fact that the proof was what found the
bugs.

  D1  RED-ON-COMPLIANT, limb (c). `grep -qF "$REF_ANCHOR"` was called without `-e`. The anchor
      begins with "- ", so grep parsed it as an option bundle, printed its usage to stderr and
      returned non-zero -- and limb (c) went RED on EVERY input including the compliant one. This
      is the exact failure shape R6 calls red-on-compliant, and only input 1 (which must keep (c)
      GREEN) could expose it. Fixed: `grep -qF -e "$REF_ANCHOR"`.

  D2  FALSE RED on the pointer literal, limb (d). The reference stores the pointer as the plain
      text `spec356-manifest.md §10`, but the natural markdown for it -- and what the synthetic
      correct edit used -- is a code span: `spec356-manifest.md` §10, with backticks INSIDE the
      string. The literal therefore never matched a realistically-written edit, and input 5, whose
      whole job is to be correct, went RED. Had this shipped unproven, wave 5's real and correct
      edit would have been graded RED on formatting. Fixed: both the before-text and the after-text
      have backticks stripped before matching, so the pointer is graded as a POINTER and not as a
      rendering.

  D3  A CONTRADICTORY EVIDENCE LINE, limb (d). The "[evidence] pointer literal is NEW in the
      after-text" line was emitted from a test against the BEFORE-text only, so it printed "NEW"
      even on inputs where the pointer was absent from the after-text and the limb had just gone
      RED for that reason -- a transcript asserting two opposite things about the same string.
      Fixed: the evidence line is emitted only when the pointer is actually present.

  Also fixed, cosmetic: the outcome-token list printed with a leading space, "PRESENT ( INDETERMINATE)".

  WHAT WOULD HAVE HAPPENED WITHOUT THE FULL FIVE-INPUT PROOF. D1 is invisible unless some input is
  required to keep (c) GREEN -- R0.5's original two-transcript scheme has one such run (the edited
  file), so D1 would probably have been caught late, at wave 5, on the real file. D2 and D3 are
  invisible unless an input is required to go GREEN on ALL limbs, which is input 5, which exists
  only because Audit v2 recommendation 4 was taken. Recommendation 4 paid for itself here.
